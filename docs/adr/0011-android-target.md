# ADR 0011: Android target

- Status: Accepted
- Date: 2026-09-07
- Supersedes: the mobile-exclusion clause of [ADR 0001](0001-platform-and-toolchain.md)

## Context

ADR 0001 scoped Dreamland to macOS and Windows desktop and explicitly put
mobile out of scope, including removing the generated mobile icon assets and
the `tauri::mobile_entry_point` attribute in commit `d4bd3a8`. That decision
stands for everything except mobile: macOS/Windows remain the primary desktop
targets, Linux remains out of scope, and the daily `mise`/uv toolchain
described there is unchanged.

Android is now a product target. Tauri 2's mobile support means the same
Rust runtime and React frontend can run there with no plugin-compatibility
problems (the `src-tauri` crate had zero `tauri-plugin-*` dependencies before
this change), but two things in the existing code assumed a desktop
filesystem and needed fixing before the app could boot or work on Android:

1. `open_download` shelled out to `open`/`cmd`/`xdg-open` per desktop OS —
   none of those binaries exist on Android.
2. `dreamland-runtime`'s path resolution (state DB, cache, config, downloads)
   is built on the `dirs` crate, which has no working concept of a
   home/config/cache directory on Android. Worse, `AppConfig::load_or_default()`
   and `RuntimeState::new()` ran before the Tauri `App` existed at all, so
   there was no way to hand them an Android-appropriate directory.

## Decision

- macOS, Windows, and Android are supported targets. Linux remains out of
  scope, unchanged from ADR 0001.
- `open_download` now goes through `tauri-plugin-opener` (Tauri's official
  cross-platform "open with the OS default handler" plugin, with native
  Android `ACTION_VIEW` support) instead of hand-rolled per-OS `Command`
  invocations.
- `run()` now constructs `AppConfig`/`RuntimeState` inside the Tauri
  `.setup()` hook, where an `AppHandle` is available, instead of before the
  `Builder` exists. On mobile, `.setup()` resolves Tauri's mobile-aware
  `app.path().app_data_dir()`/`app_cache_dir()` and exports them as the
  `XDG_DATA_HOME`/`XDG_CACHE_HOME`/`XDG_STATE_HOME`/`XDG_CONFIG_HOME`/
  `DREAMLAND_DOWNLOAD_DIR` environment variables that `dreamland-runtime`'s
  path functions already prefer over `dirs::*`. Desktop behavior is
  unchanged: those variables stay unset there, so the existing `dirs`-based
  fallbacks apply exactly as before.
- The five icon assets and `mipmap-*`/Android project files commit `d4bd3a8`
  removed are regenerated by `tauri android init` into `src-tauri/gen/android`
  rather than restored by hand.

## Known issue: hidden auxiliary windows aren't hidden on Android

`begin_auth`/`auth_status` open a second `WebviewWindow` pointed at yandere's
login page with `.visible(false)`, to read auth cookies out of it without the
user seeing it — a desktop pattern relying on Tauri's multi-window support.
Android has no real multi-window model: that "hidden" window becomes the
actual visible Activity content, so on load the app was replaced full-screen
by yandere's own (broken-URL) login page, which itself 404s server-side
("Requested page does not exist / Return to index") — not a dreamland bug,
but yandere's own 404 HTML rendering where the app should be. The frontend's
`authQuery` (`src/App.tsx:659-664`) fires this automatically on load whenever
the active/default site is yandere, so this hit on every cold start, not just
when a user chose to sign in.

**Fix:** `begin_auth` and `auth_status` (and `yande_auth_window` itself) are
now `#[cfg(not(mobile))]`-gated in `src-tauri/src/lib.rs`, with `#[cfg(mobile)]`
counterparts that never create a window: `auth_status` returns
`{authenticated: false, username: None}`, `begin_auth` returns a clear error.
Android v1 ships without yandere sign-in — favorites, pool ZIP downloads, and
other auth-gated capabilities are unavailable there until a real Android
auth flow (e.g. an Android-native cookie-jar plugin, or a visible in-app
browser tab the user explicitly closes) replaces this pattern. Not addressed
here; `open_site`/`open_post`/`open_similar_search` also open extra
`WebviewWindow`s (visible ones, so not hit by this same bug) and inherit the
same "Android doesn't really have multiple windows" caveat if a user opens
one — navigating away from the main app view with no way back is a known,
unaddressed rough edge.

## Known issue: `wry` 0.55.1's `getCookies()` crashes on first launch

On-device testing (Android 15, WebView 140, OnePlus 8) surfaced a crash that
had nothing to do with dreamland's own code: `wry`'s generated
`RustWebView.kt` declares `fun getCookies(url: String): String` (non-null)
but implements it as `return cookieManager.getCookie(url)`, and
`CookieManager.getCookie()` legitimately returns `null` whenever no cookie
exists yet for a URL — always true on first launch, before any site has set
one. Kotlin's compiler inserts a runtime null-check on that return, which
throws inside a JNI call from Chromium's native WebView code. Native code
doesn't clear the resulting pending exception, so the *next* unrelated JNI
call anywhere in the process aborts the whole app (`JNI DETECTED ERROR ...
getCookie(...) must not be null`) in debug builds; in release builds R8
instead strips the method as apparently-unreachable (no `-keep` rule exists
for it), producing `NoSuchMethodError` instead. Confirmed by reading
`wry-0.55.1`'s own source
(`~/.cargo/registry/.../wry-0.55.1/src/android/kotlin/RustWebView.kt`) — this
is an upstream bug, not something introduced here.

**Current workaround (not durable):** the one-line fix
(`cookieManager.getCookie(url) ?: ""`) is applied directly to the `wry`
crate's source in this machine's local Cargo registry cache. `src-tauri/gen/`
is gitignored and Tauri regenerates `RustWebView.kt` from that cached
template on every `tauri android build`/`dev` invocation, so this patch:

- Is invisible to git and does not travel with the repo.
- Is lost if the Cargo registry cache is cleared or `wry` is refetched.
- Must be re-applied by hand on any other machine (or after a cache clear)
  before an Android build will boot past first launch.

Durable follow-up options, not yet done: report/patch upstream in `wry`, or
add a `[patch.crates-io]` override in the workspace `Cargo.toml` pointing at
a vendored or forked copy of `wry` with the fix. Until one of those lands,
**a fresh machine cannot get a working Android build of dreamland without
first re-applying this patch to the Cargo registry cache by hand.**

Release builds have a second, separate gap even with the source fixed:
R8 needs a `-keep` rule for JNI-invoked Kotlin methods like `getCookies()`
in `app/proguard-rules.pro`, or it will continue stripping them regardless.
Not yet added — debug builds were the verification target for this ADR.

## Addendum (2026-09-07): shared-gallery downloads, notifications, and a `Platform` trait

Three more gaps found via `docs/ANDROID-ASSET-AND-DETAIL-AUDIT.md` and a
comparison against the vendored `moebooru` reference, all fixed and verified
on-device:

- **Downloads now also land in `Pictures/Dreamland/`** via
  `tauri-plugin-android-fs`'s `PublicStorage::write_new`, matching
  moebooru's own `Pictures/$moeHost` `MediaStore` convention. The original
  app-private copy (`app_data_dir/images/...`) is left in place unchanged —
  the rest of the app (dedup checks, `open_download`, thumbnails) keeps
  working from that path; the Pictures copy is a best-effort side effect
  published after a download completes, via a new
  `DownloadManager::subscribe_completions()` broadcast channel.
- **Downloads now trigger a system notification** via
  `tauri-plugin-notification`. Android 13+ (API 33) requires an explicit
  runtime `POST_NOTIFICATIONS` prompt in addition to the manifest permission
  (which the plugin injects automatically via its own AAR manifest merge —
  it does not appear in the source `AndroidManifest.xml`, only in the
  Gradle-merged build output); without calling `request_permission()`, the
  notification channel exists but nothing is ever shown
  (`dumpsys notification` reports `importance=NONE`). Requested once, at the
  start of the same completion-handling task that does the gallery publish.
- **`src-tauri/src/lib.rs`'s scattered `#[cfg(mobile)]`/`#[cfg(not(mobile))]`
  duplicated-function pairs were replaced with a `Platform` trait**
  (`src-tauri/src/platform.rs`), with `Desktop`/`Mobile` structs implementing
  it and a single `ActivePlatform` type alias selecting between them at
  compile time. Each `#[tauri::command]` is now a single definition that
  delegates to `ActivePlatform::method(...)`, rather than two full duplicated
  function bodies gated by `cfg`. The trait bound means adding a new
  platform-divergent behavior forces both implementations to cover it.

## Consequences

- Frontend touch ergonomics (`App.tsx`'s wheel/keydown/mousemove-driven
  chrome) are not addressed by this ADR. Pointer events already fire on
  touch, so the app is usable, just not touch-optimized; that is a follow-up
  once there is a build to test on-device.
- Android SDK/NDK, and the `aarch64`/`armv7`/`i686`/`x86_64`-linux-android
  Rust targets, join the OS-level prerequisites `.mise.toml` already
  documents it does not manage.
- This is a debug-APK capable target, not a signed Play Store release;
  release signing is out of scope for this ADR.
